## Findings

### P1 — targeted NPC spells can use target AC as casting difficulty — corrected

The defect is in the installed Shadowdark 4.0.6 sequence used by our launcher:

1. `NpcSD.castSpell()` calls `shadowdark.dice.setRollTarget(config)`.
2. `setRollTarget()` seeds `config.mainRoll.dc` with the selected target's AC.
3. `NpcSD._generateSpellConfig()` then uses `config.mainRoll.dc ??= spell.system.dc`.
4. The existing AC prevents the Spell Item's casting difficulty from being used.

A Tier 2 spell against AC 18 therefore receives DC 18 rather than DC 12. This
occurs when Shadowdark targeting is enabled and a target already exists at cast
creation. It does not establish that every spell or every casting route is broken:
the Player generator uses a direct assignment and normally selects the correct DC.

Our player-targeting code already kept spell selection separate from attack AC
assignment; it did not introduce the underlying NPC generator defect. The module
nevertheless lacked a correction at that integration boundary and its tests did
not exercise the native preselected-target sequence.

The correction:

- Resolves the Spell Item and supplies its effective casting DC before Quick
  Spell calls the native casting method. The fallback is `10 + tier` if the Item
  does not expose its derived `system.dc`.
- Routes NPC spell switching in the merged dialog through the same launcher.
- Normalizes spell DC on native dialog rendering and at the Player/NPC spell
  hooks, including casts with no targeting panel or skipped prompts.
- Corrects copied spell configurations in both module reroll paths, without
  changing historical cards.
- Leaves attack and attribute-check difficulties untouched.

No Actor/Item data or persisted settings are rewritten. Core and system source
remain read-only.

### P2 — legacy client settings can overwrite newer preferences — corrected in 1.1.3

`scripts/migration.mjs`, `migrateSettings()` and `migrateLegacyModuleId()`.

`migrateLegacyModuleId()` runs client migration before checking the world migration
marker. `migrateSettings()` copies every legacy stored value without checking
whether the new namespace already has a stored value or recording that this
client finished migration. The legacy client values remain in storage.

Reproduced: migrate an old `defaultChosenAttacks = one`, change the new preference
to `all`, then call migration again. It returns to `one`. The earlier README claim
that existing new values are never overwritten was accurate for document flags,
but not for settings; the wording has been corrected.

Resolution: both client and world migration now check for explicitly stored
current values before copying. A new hidden client setting,
`legacyClientIdMigration`, records successful completion once. Failed storage
writes leave completion unset for retry. Existing values are preserved even when
false, zero, null, empty, or equal to a default. The regression suite verifies a
changed preference survives the next migration and tests failed-write recovery.

### P2 — Focus spell rerolls can mark a spell lost — corrected in 1.1.3

`scripts/chat-reroll-mode.mjs`, `synchronizeSpellReroll()`.

The function sets `system.lost` from `!result.success` for known spells without
checking `config.cast.focus`. Shadowdark's initial Player casting path explicitly
exempts a failed Focus cast from losing the spell. The module's reroll and undo
paths do not preserve that exemption.

Reproduced: reroll a known Focus spell with a failed result; the update is
`{"system.lost": true}`. This is separate from the DC correction.

Resolution: the known-spell branch checks the actual Actor type and Focus state.
Player Focus failures keep the spell available, including when undo restores an
original failed Focus cast. NPC spell loss and wand failure/breakage still use
their distinct native behavior. Regression tests cover those cases and ordinary
spell loss/recovery.

### P2 — save requests trust the request ID without verifying the check — corrected in 1.1.3

`scripts/save-requests.mjs`, `settleSaveRequestFromRoll()`.

The GM settlement path checks the request ID and `roll.success`, but does not
verify the rolled Actor, requested ability, requested DC, or the message author's
permission to answer. The UI checks ownership before launching the check, but the
GM's settlement entry point still accepts mismatched cards.

Reproduced: a pending STR DC 12 request for Actor A is settled as resisted by a
WIS DC 1 check for Actor B carrying the same request ID. No real world documents
were modified during the reproduction.

Resolution: settlement now verifies a check roll for the same resolved Actor and
requested ability, and verifies the request DC in both configuration and actual
main-roll options. The author is resolved from Foundry's User collection and must
be a GM or an owner of the target. Mismatches leave the request pending. The
resolution lock covers asynchronous validation so concurrent cards cannot settle
one request twice. Tests include a correct owner response, a matching GM Token
Actor response, an unauthorized author, and mismatched Actor/ability/DC/type.

### P2 — inside-gullet damage is counted separately per swallowed token — corrected in 1.1.3

`scripts/swallow-system.mjs`, `onDamageApplied()`.

Damage accumulation is stored only on the swallowed source token. If two swallowed
characters deal 8 and 7 damage in the same round, their separate totals are 8 and
7; neither reaches the threshold of 15, so they are not released. The original
requested behavior describes cumulative damage from the swallowed creatures in
that round. A shared per-swallower total, keyed by combat and round, is needed.
This finding comes from source inspection; it was not exercised in live Foundry.

Resolution: `swallowGulletDamage` is a new module-owned flag on the swallower
Token. Its combat ID, round, and total combine damage from every creature inside
that swallower. Per-swallower queues serialize simultaneous writes. Different
swallowers, combats, and rounds stay independent, and healing is excluded.
Tests verify 8 + 7 releases both creatures, including concurrent events.
Old swallowed flags and their counters are retained, but old totals are not
imported because their combat cannot be identified. The new tally starts fresh
on upgrade. Round-based accumulation requires an active combat; the existing
manual release remains usable outside combat.

## Current architecture assessment

The feature boundaries remain useful: targeting, quick launchers, roll-dialog
selectors, chat presentation, declarative rules, save requests, and migrations
are separate modules. Quick Spell delegates to Shadowdark's casting workflow,
preserving casting ability bonuses, spell loss, scroll consumption, and wand
handling. The spell DC bug illustrates why integration tests must include the
system's configuration order, not only assertions against mocked cast arguments.

The rule engine validates declarative data instead of executing arbitrary user
JavaScript. Preset application copies rule snapshots into Items. World changes
and consequences generally use active-GM resolution. The existing tests cover
many state transitions, but passing the mocked smoke suite does not prove live
DOM layout, hook ordering with all installed modules, or multiplayer behavior.

The current built-in presets are Gore, Crush, Charge, Ambush, Rampage, Backstab,
Assassinate, Algae-Eater, Shatter, Mob, Pod Hunter, Swallow, Grab, Rage, Greedy,
Poison (Damage), Poison (Paralyze), Poison (Sleep), Poison (Lethal), Petrify,
Knock, Ability Drain, and Sever.
